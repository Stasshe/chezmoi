# LP

基準は、初めて来た意思決定者が見た瞬間にわかり、浮かんだ反論に次の段で答えがあること。正しいだけの文章と、並んだだけの箱を作らない。

## 始める前に

1. 読者を決める。役員など非エンジニアが読むなら、頭の固い年配の役員でもわかるかを全文の基準にする。
2. 既存サイト、過去版、見本を実際に描画して見る。良いと言われた版は全部見る。
3. 既存があれば品質の下限にする。ゼロから作り直さない。そのまま移すのでもない。良い所から始めて全節を上回る。
4. 事業の正本を、抜粋でなく通して読む。強みのメモ、設計の意図文書、営業資料（たとえ話と比較の枚）、根拠と実績の記録、競合調査。書いてよい事実はそこから取る。核の一文は、意図文書や強みのメモに既に書いてあることが多い。
5. 前後の節を読む。同じ主張、同じ図の型を重ねない。

## 核を掘る

- その位置で読者が抱く疑問を書き出す。疑問は連鎖する（例:「汎用の道具で足りるのでは？」→「自動で回せば同じでは？」→「データはどこに置かれる？」）。節はその順に答える。
- 主張の候補を全部出し、候補ごとに次の3つを作業メモに書いてから作る。
  - 反論: 読者か、その部下のエンジニアが言う最も強い反論。崩れる主張は差ではない。
  - 固有: 比較相手もできることは、相手との差にしない。自社の仕組みの節で扱う。
  - 根拠: 正本にあるか。自社観測だけの主張、比較条件のない費用は出さない。
- 差は機能、部品、作る手間には出ない。時間がたつと何が起きるか、どこで何が起きるかの場面に出る。部品の表は「作ればいい」で終わる。
- 落ちる主張: 相手も設定や工夫で同じ状態にできるもの（稼働時間、機能の有無、そろった仕組み）。相手も持つ機能。
- 通る主張の型
  - 時間: 使い続けると結果が分かれる（積み上がる／毎回やり直す）。
  - 人: 誰かが毎回動かす必要があるか。
  - 場所: データや処理が外へ出るか、自社専用の中で完結するか。
- 試験を通った主張は並べてよい。1つの核に急いで絞らない。
- 最初の思いつきを出さない。結論を出したら反論に戻し、正本を読み直す。
- 核を依頼者に質問で返さない。掘るのはこちらの仕事。質問は、資料にない事実と依頼者しか持たない判断だけ。

## 別の目

主張を決める前にCodexと議論する。`codex exec` は使わない。

1. tmuxでshellだけ起こし、`send-keys` で `codex` を起動する。`Ask Codex` が出るまで待つ。
2. 依頼文をscratchpadのファイルに書く。読者、正本のパス、依頼者の反応（原文）、今の案、外した案と理由、聞きたいこと、「言い切ってよい。事実と違う言い切りだけ、正しい言い切りに直せ」、回答の書き出し先。
3. 「<依頼文のパス>を読んで答えて」を送り、別の呼び出しで `Enter`。`capture-pane` で `Working` を見るまで送信済みとしない。
4. 回答はファイルに書かせて読む。TUIの画面履歴では長い回答の頭が切れる。
5. 採るのは事実の訂正だけ。良いと言われた要素を消す案、言い切りをぼかす案は採らず、理由を報告に書く。
6. 終わったらsessionを閉じる。

## 違いを伝える節

- 疑問（「」付きの小さな一行）→ 一言の答え（見出し）→ 相手と自社の対比の絵 → 各1文のキャプション。疑問の連鎖の順に並べる。
- 相手の強みは一言で認める（「優秀な道具」）。「できます。ただし」と譲って締めない。
- 主張は絵で伝える。表は頭に入らない。表は製品を並べて選ぶ細部の確認に使う。
- 対比の絵は、通る主張の型ごとに作る。
  - 時間: 同じコマを時点ごとに並べ、1か所だけ変える。自社側だけ積み上がり、相手側は毎回同じ。
  - 人: 人が毎回動かす場面と、人がいない間も進む場面。
  - 場所: 相手側はデータが枠の外へ出て、自社側は枠の中で完結する。

## 文章

- 言い切る。「設計です」「想定」「考え方です」「〜してみませんか」「この例では」を使わない。
- 依頼者が決めた主張に、弱める注記やリスクの指摘を足さない。強い言葉を求められたら、そのまま書く。
- 見出し直下、リード、図には、一目で要ることだけ置く。停止条件、契約、SLAなどの細部はFAQへ。同じ但し書きを繰り返さない。
- 判断軸は「事実か」だけでなく「その場所に要るか」。
- 「準備中」「提供時期」など水を差す話は、聞かれていなければ書かない。問い合わせの後でよい。
- 費用、契約の細目は、確定した範囲だけ。無理に載せない。
- 非エンジニア向けにコードを画面に出さない。専門用語は普段の言葉へ。技術の詳細はFAQの回答に留める。
- 同語反復（「構成と費用を相談／構成と費用をご案内します」）と自明な文を消す。
- FAQは1文目で問いに答える。答えが問いに対応しているか、全問読んで確かめる。
- 他社との違いは控えめな一文にしない。主張は絵の節で言い切り、比較表は細部の確認に使う。表では自社の列を強調し、見出しでも比較と言う。
- 根拠の薄い実績数値は、出すと弱く見えるなら載せない。数字を作らない。

## 見せ方

- 各節を、文字より先に挿絵か図で伝える。ヒーローは動きのある図が強い。停止ボタン、動きを減らす設定、JSなしの静止画を付ける。
- 買い手が最初に知りたい内容を折りたたまない。折りたたみはFAQの回答だけ。二重の開閉にしない。
- 左端を全節で揃える。一部の節だけ中央の細い段組みにしない。
- 問い合わせは締めくくりの独立した節にする。全幅の色帯で、白いフォームを載せる。白地に白のフォームは問い合わせに見えない。
- CTAは1色に統一する。
- 短い内容の横に大きな穴を作らない。列の重さ、上端、下端を揃える。
- 日本語は文節で折る（BudouXなど）。語の途中、「Web・/API」、1文字だけの行を残さない。
- 英字の見出しラベルは飾りで、非エンジニアには要らない。依頼がなければ付けない。
- 狭い幅のナビは開閉式にする。上段に相談ボタンを常に見せ、メニューは文字ボタンにできる。横スクロールのナビにしない。
- 機器や仕様の例を主役にしない。暫定のものを専用品のように見せない。

### 絵の作り

- 同じものは節の中で同じ絵にする（処理する主体、外部のサービス、会社の境界、蓄積したものなど）。
- 対比は同じ枠と縮尺で並べ、自社側だけ強調色の枠にする。変えるのは比べる1点だけ。
- 絵の中の文字は短い吹き出しとラベルだけ。説明はHTMLのキャプションに置く。狭幅で縮んでも読める大きさにする。
- SVGはインライン。意味のある絵は `role="img"` と `aria-label`、飾りは `aria-hidden` にして文字を本文に置く。

## 確認

- 実ブラウザで320、375、768、1024、1180、1440、1920。切り替わる幅の前後も見る。
- 全文を読者になって通読してから完了と言う。浮かんだ反論に答えがあるかも見る。指摘されるまで待たない。
- 既存版と同じ幅で節ごとに並べて比べる。部分の改善で全体が悪化していないか見る。
- 全面スクショでは遅延読み込みの画像が空白になる。空白を見たら、スクロールしてから判定する。
- 委譲先の「完了」を信じない。自分で画面を見る。修正で別の所が壊れていないかも見る。
- フォームは実際に送信し、エラー表示と成功表示を見る。

## 依頼の読み方

- 言葉どおりに受け取る。「この見た目がいい」は節全体の話で、細部まで好きとは限らない。
- 否定を広げない。「キモい」と言われたのがその形か、機能そのものかを取り違えない。
- 見本の画像は、文言とラベルまで正本。他の方針を適用する時も崩さない。
- 対象や範囲の解釈が割れて、やり直しが大きくなるなら、動く前に一言確認する。主張の核は確認せず掘る。
- 判断と、載せなかった主張の理由は、docsの意図文書に誰の判断か分けて書く。メモリに逃がさない。
- 委譲するときは指摘を原文のまま渡す。Claude側の解釈を足すなら、解釈と明記する。
- 評価の言葉
  - 「良さげ」: 芯として残し、周りを組み直す。前の版でも良いと言われた絵は捨てない。
  - 「全然まだ」: 手直しでなく掘り直し。正本に戻る。
  - 「そこじゃない」: 軸の誤り。言い方を変えても直らない。
  - 「考えろ」「すぐに結論を出すな」: 質問と早い結論をやめ、候補と反論を出し直す。
  - 「1個に絞らなくて良い」: 試験を通った主張を並べる。

## 失敗例（実際にあった）

- 直前の節と同じ主張を違いとして出し、反論一つで崩れた。
- 反論に押されて「できます。ただし」と譲り、部品の表にした。軸がずれ、表は読まれなかった。
- 核を依頼者に選択肢で質問した。
- 正本を抜粋で読み、最初の思いつきを核にした。核の一文は設計の意図文書にあった。
- 別のAIの回答を画面履歴から読み、頭が切れた。別のAIは言い切りを外し、良いと言われた要素まで消す提案をする。

## 技術の既定

静的なLPならAstro。問い合わせAPIが要ればHonoを足す。フォントは `@fontsource` でnpmから入れ、バイナリをGitに入れない。ページ部品はコンポーネントに分け、CSSの `!important` を積まない。
