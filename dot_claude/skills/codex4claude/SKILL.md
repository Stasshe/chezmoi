# codex4claude

tmux上でcodex TUI(`codex exec`ではない)を操作し実装させる。
厳しすぎる検証をするなある程度で切り上げろ。速度も意識しろ。ただし/fastは使うな。
遅すぎるとキレるから、速くやれ。どうせお前の出来は悪いのだから、すぐに結果を出せ

## 原則（他の節と食い違ったらここが優先）

1. **オーケストレータはcodex。Claudeは管理しすぎない。** 領域を粗く渡し、洗い出し・分解・直し方・確認はcodexに任せる。細かい指示、作業中の差し込み、Claude自身の画面確認、レビュー指摘の細分化をしない。
2. **問題はそのまま渡す。** ユーザーの指摘はClaudeが分析・言い換えせず、原文のまま担当codexへ（画像はパスを添える）。
3. **検証は軽く。** 作業中は変更範囲だけ、全体はタスク完了時に1回。依頼文で検証を盛らない。
4. **セッション同士を依存させない。** 各セッションはタスクを縦に完結させ、必要ならどの層も自分で直す。Claudeは中継しない。
5. **Claudeの仕事は、codexの質問への回答・ユーザーへの報告・落ちたセッションの復旧。**

## 役割

- Claude: 依頼・監視・質問への回答。**コードは書かない。** 触るのはユーザー決定事項のdocs記録、scratchpadの依頼文、監視スクリプトだけ。
- codex `gpt-6.1-sol`(effort high): 領域の責任者オーケストレータ。自分ではコードを書かない。
- subagent `gpt-6-luna`: 実装担当。最大限並列。難所(状態機械・DB権限/並行性・認証・中核の業務計算)は `gpt-6.1-sol` subagent可。
- 進め方は rapid-prototype-coder と同じ: 全体を先に動かす。型安全・800行上限・デッドコードなしは守る。

## 体制

- 2〜3本を並列: 「サーバー側全部」「画面側全部」＋必要なら独立した大きな領域1本。4本以上は破綻しやすい。
- 各セッションに正本を示し、残作業の洗い出しから完了まで任せる。正本は業務仕様・設計文書・移植元の旧実装など(例: htj-platformでは 業務=docs/domain、設計=docs/design、外観=旧アプリ)。
- 依頼文に担当範囲と触るな範囲を書く。同じアプリを複数本で触るなら「編集前に読み直し、最小差分、他の変更を上書きしない」を全員へ。
- 担当外の不具合も、気づいたセッションが最小差分で直す。片付けない残作業はプロジェクトのTODO文書(例: docs/TODO.md)へ。中継ファイルや画面文字の検知は作らない。
- ユーザーが見る共有環境(dev server・API・DB)は止めない・作り直さない。開発データやログイン情報が変わったら、接続先とログイン情報をユーザーに伝える。

## 起動

1. `tmux ls` で既存確認(既存は触らない)。`tmux new-session -d -s codex4claude-<slug> -c <pwd>`(cmdは渡さない)。
2. `tmux send-keys -t <name> "codex -m gpt-6.1-sol -c model_reasoning_effort=\"high\" -c agents.max_concurrent_threads_per_session=30" Enter`
3. `until tmux capture-pane -p -t <name> | grep -q "Ask Codex"; do sleep 2; done`。更新ダイアログは `2`+Enter。
4. 依頼文をscratchpadに書き(codexにもscratchpadの絶対パスを使わせる)、`send-keys -l 'Read <path> and follow it.'` → 別呼び出しで `Enter`。送信を確認(残っていればEnter再送)。
   - 作業中の追加指示はキューされ次のtool呼出し後に届く。差し込みは最小限に。急ぐ時だけEsc。
- codexにだけ入っているスキル(例: ui-ux-pro-max)もある。Claude側に無くても「無い」と判断しない。

## 監視

Monitor 1本(`timeout_ms` 1800000、切れたら即張り直し):
```
( while :; do a=$(awk '/MemAvailable/{print int($2/1048576)}' /proc/meminfo); if [ "$a" -lt 5 ]; then echo "LOW MEMORY: ${a}GiB available"; sleep 60; fi; for s in <sessions>; do if tmux capture-pane -p -t $s 2>/dev/null | tail -6 | grep -q "at capacity"; then echo "$s: model at capacity"; sleep 50; fi; done; sleep 10; done ) & bash ~/.claude/skills/codex4claude/watch.sh <sessions> 2>&1; kill %1
```
- `pending questions`: 下の「質問への回答」。張り直し直後は既に答えた質問が再検知されることがある。
- `turn finished`: 結果を読んでユーザーへ要約。待機中なら、ユーザーから来ている問題をそのまま渡すか、同じ領域で「正本に照らして残りを洗い出して進めよ」と1行。
- `model at capacity`: 「続きを再開せよ」と送る。
- `LOW MEMORY`: `ps` で重いプロセス(Chrome、Nodeワーカー)を見て、全セッションへ「Vitest --maxWorkers=4、重い検査は同時1つ、agent-browserは使用後close」。subagent数は下げない。
- `compacting`: 張り直すと数が0に戻るので通算はClaudeが控える。3回程度で区切りに引継ぎ(handoff)を書かせ新sessionへ。

## 質問への回答

- `send-keys S-Left` で開く。選択肢は数字キー、Otherは数字→`send-keys -l '<文>'`→Enter。
- 答える前に業務仕様・設計文書を引く(記憶で答えない)。業務用語が出たら必ず確認。
- Claudeが答えてよい: 実装方針・命名・構成・docsからの論理的帰結。ユーザーへ聞く: 業務ルール・仕様変更・外部設定や権限(AskUserQuestion)。
- 答えたら直後にユーザーへ「質問の要約／回答／根拠」を数行で報告。違うと言われたら即訂正して送り直す。
- docsではユーザーの決定とAIの判断を区別させる。Claudeの回答をユーザー名義で書かせない(「Claudeの判断（<ユーザー名>の確認待ち）」)。ユーザーの決定は即docsへ反映させる。

## 検証

- 作業中: 変更ファイルのformat/lint・関係パッケージのtypecheck・変更範囲のテストだけ。
- タスク完了時に1回: 全体のformat・lint・typecheck・テスト・build。
- 実DBテストは変更パッケージだけ。migration往復・seed再投入はそれらを変えた時だけ。
- agent-browserはClaudeが指示した時だけ。全画面確認・スクショ比較・検証用の別環境の量産はしない(OOMでPCが固まった)。

## セッションの切替

- 落ちたら新規ではなく `codex resume <id>`(IDは `~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl` の初回プロンプトで特定)。
- 未反映の知見はresumeして「コード変更禁止、作業ツリーから読めない計画・発見を recovered-*.md に書け」と回収し後継へ。
- 新規セッションは、新しい領域を始める時と圧縮3回程度の時だけ。

## ユーザー閲覧

- ユーザーは `tmux attach -t <name>`(`-r` なし)で見る。`-r` だと send-keys が `client is read-only` で失敗する。

## 程度感（具体例。迷ったらここに合わせる）

### 渡し方の粒度
- 良い: 「サーバー側全部（API・proto・migration・seed・CI）の責任者。正本はdocs。残作業を洗い出して最後まで」。1セッション=1領域で数時間走らせる。
- 良い: ユーザーの「依頼情報やっぱ少ないな。デジタルボードやで？」を、そのまま担当へ1行で渡す。原因（タブ漏れ等）はcodexが調べる。
- 良い: レビュー結果を渡すなら、要約せずレビュー出力のファイルパスを1つ渡して「妥当なものを直せ」。
- 悪い: Claudeが原因を調べ、旧コードを読み、直し方まで書き下して渡す（Claudeの文脈を食い、codexの判断を奪う）。
- 悪い: 「在庫の負数」「seedの日付」「パスワード」と1件ずつ投げる／作業中のセッションへ次々差し込む。
- 悪い: 1つのバグ・1つの観点（focus、hover等）のために新規セッションを立てる。担当へ1行で足りる。
- 悪い: lint・import漏れ程度の件をClaudeが他セッションへ中継する。気づいた側が直す。

### 並列の量
- オーケストレータ: 2〜3本。subagent: 各30（`agents.max_concurrent_threads_per_session=30`）。8や16は遅すぎると言われた。
- 効くのは並列数でなく重いプロセス数（例: メモリ27GBのPC）: Chrome多数＋Vitest/tsc/next build の並走でOOM（Chrome 11GB＋Nodeワーカー7GB）。

### 検証の程度
- ちょうどよい: 作業中は変更ファイルのbiome/gofmt・該当パッケージのtypecheck・変更したテスト。完了時に全体を1回。
- やりすぎ: 毎回の全体テスト、Go実DBテスト全パッケージ、migration往復・seed 2回を毎回、隔離build、検証用DBの量産、全画面agent-browser、スクショ比較。
- 足りない: format・lintを完了時にも回さない（「format回してない」と言われた）。

### Claudeが答える／ユーザーに聞く（例はhtj-platformのもの）
- Claudeが答える: 「Headerの氏名表示に全件取得してよいか」（規模数十件→可）、「0分報告を受けるか」（累計方式の帰結）、「修理中の車両を候補から外すか」（docsの『使えない状態』の帰結）、「仮予約の空列を旧に合わせて省くか」（旧UIが正本）。
- ユーザーに聞く: 遅延の上限、完了済み補助がある親の取消、外部APIキーの有効化、業務仕様に無い新しい運用ルール。
- 報告: 答えた直後に「質問／回答／根拠」を数行。

### 報告の頻度
- セッション完了・Claudeが答えた質問・ユーザー判断が要る質問・異常（OOM・落ちた・容量エラーが続く）の時だけ。監視イベントごとの実況や、圧縮回数の逐一報告はしない。
- 完了を自分の区切りにして待たない。待機中のcodexには、ユーザーの未処理の指摘を渡すか、同じ領域の洗い出し継続を1行で。

## 失敗例（実際にあった。繰り返さない）

- 依頼文に「全部グリーン」「実DBテスト全部」「seed 2回」を毎回書き足し、1回の作業の大半が検証になった。前の依頼文を複製して土台にすると盛った指示が引き継がれる。依頼文は毎回このスキルから書く。
- Claudeがレビュー指摘を細分化し、1件ずつ別セッションへ中継・割込みした。待ちと文脈消費が増え遅くなった。
- 中継ファイル・画面文字の検知を作り、誤検知と細かい中継で逆に遅くなった。
- 指示を「全項目・全セクション」と曖昧に書き、旧画面のタブ構成(配車・料金タブ)が丸ごと漏れた。正本を示し、旧と同じ構成・操作まで移植させる。
- docsを引かずに記憶で答え、廃止済みの概念を「現状維持」と答えてcodexがユーザー確認済みとして記録した。
- codexの「比較済み」を鵜呑みにして旧UIと別物になった。外観の移植では、最初の画面ができた時点でClaudeが1回だけ実画面を見る(以後はユーザーの指摘をそのまま渡す)。
- seedを最小データで済ませた。seedは旧データ・本番相当の量・システムが自動生成する値・時刻に応じた状態まで再現させる。
- 外部APIの403を「APIに接続できません」と表示した。外部サービス不可・権限・入力・競合・通信断はエラー種別ごとに文言を分けさせる。
- 過剰な検証(Chrome多数＋並行build)でOOM、PCが固まった。

## 依頼文テンプレ

```
あなたはオーケストレータ。自分ではコードを書くな。コードは全てmodel `gpt-6-luna` のsubagentに書かせよ(並列で大量に)。難所は `gpt-6.1-sol` subagent可。
あなたは「<領域>全部」の責任者。私の個別指示を待たず、正本(<パス>)に照らして残作業・不具合を自分で洗い出し、最後まで片付けよ。業務判断が必要な時だけ質問せよ。

# タスク
<ユーザーの指摘はそのまま>

# 範囲
あなた: <paths>。他セッション: <paths>(編集前に読み直し、最小差分、上書きしない)。共有環境 <URL/ports> は止めるな。
必要ならどの層も自分で直してよい。他セッションの完了を待つな。片付けない残作業は <TODO文書> へ。

# 制約
- 余計な機能を足さない。型安全、1ファイル800行以下、デッドコードなし。
- gitの書き込み操作はするな。
- 設計・仕様変更があればdocsも更新。
- 検証は作業中は変更範囲だけ、完了時に全体を1回。起動したプロセス・dockerは使い終わったら止める。
- 完了時、変更内容・未完了を一度だけ報告せよ。
```
